# Uplink signed operator plans, not Python containers

This page gives the study on moving OpenTSx time-series operators onto satellite onboard computers and FPGAs through an Apache Wayang operator library, including in-orbit storage services and pre-flight test environments; all sources were accessed on 2026-11-19.

Status: code facts refer to commit `073d4b5` of kamir/OpenTSx (2026-11-19). Statements about commercial products and announced missions come from vendor documentation, agency pages or press releases and are vendor claims unless another source is named.

Converting the OpenTSx Python time-series operators into FPGA logic is not possible as a code conversion, and the Python package is the wrong place to start: no maintained tool in November 2026 compiles NumPy, SciPy or statsmodels code to FPGA logic, and the Python operators (DFA, MFDFA, RIS, event synchronization, Welch, STL, SARIMAX) are batch routines built on whole-series statistics, least-squares fits and iterative optimizers that have no hardware form. A standard operator library that Wayang places across tiers, so that orbit receives signed plans instead of Python containers, is feasible and about half-built: OpenTSx already has a frozen 16-operator catalog with shared f64 parity vectors, a Rust runner that executes 15 of those operators as static ARM binaries, a Wayang `RustPlatform` that hands complete bounded stages to non-JVM workers, and Ed25519-signed plans that name operator ids and never carry code. The recommended design keeps Wayang on the ground (Tier 1), runs the Rust runner on a Linux-class onboard computer against a local Kafka-protocol log (Tier 2), and adds a small FPGA kernel pack that reduces raw ring-buffer samples to exact integer window partials which the Rust runner finishes in f64 (Tier 3); two new Wayang platforms compile and sign one plan bundle per contact window instead of waiting on remote stages. The link budget is the reason to do it: an illustrative 1,000-channel, 1 kHz, 16-bit feed produces about 173 GB per day, 460 times what one S-band ground station downlinks, while per-minute window statistics of the same feed need 144 to 288 MB. Nobody offers S3 in orbit and no hosted-app platform gives containers object storage or a documented route to ground S3, so S3 belongs on the ground and the onboard log should be a local, non-S3 log whose sealed segments are downlinked into ground S3. The remaining blockers are contractual rather than physical: every OpenTSx tolerance assumes IEEE f64, signed admission covers only pass-through today, no Kafka-protocol broker has flown, and the repository declares FPGA work out of scope, so Tier 3 needs a decision record before any code.

## No compiler turns the Python TSA package into FPGA logic

The Python package is a batch, whole-array library. Its core dependencies are NumPy, pandas, SciPy, fastavro and xxhash, with statsmodels as an optional extra (`python-package/pyproject.toml:28-39`), yet `_analysis.py` imports statsmodels at module top and the spectral and RMS modules import from it (`python-package/opentsx/algorithms/_analysis.py:8`), so even the smallest container would carry statsmodels. Every long-range and event operator starts from a whole-series statistic. DFA and MFDFA subtract a global mean, take a cumulative sum and fit `np.polyfit` per segment (`python-package/opentsx/algorithms/dfa.py:70-135`, `mfdfa.py:91-175`); event synchronization thresholds at `mean + 2*std` or the 95th percentile of the entire series (`event_sync.py:99-113`); RIS takes a global percentile and hard-codes `gamma = 1.0` inside a bare `except` (`ris.py:157-165`). Decomposition and forecasting call statsmodels STL, MSTL and SARIMAX fitted with L-BFGS for up to 200 iterations (`decomposition.py:38-40`, `forecasting.py:42-104`). **None of these operators has shared cross-runtime test vectors** (`docs/learning/library-operators.v1.json`; Concept 20:303), and no processor description declares a `python` runtime. Only two Python paths touch Kafka: a snapshot registry that exposes Welch and episode RMS, and a SARIMAX scoring worker that advances a pre-fitted Kalman state (`python-package/opentsx/client/research.py:17-36`, `python-package/opentsx/client/scoring.py:510-512`).

No compiler closes that gap. DaCe is the only general NumPy-to-FPGA compiler, but its FPGA backend now sits in a side repository validated against Vitis HLS 2020.x and 2021.x on Alveo u250 and u280 cards ([spcl/dace-fpga](https://github.com/spcl/dace-fpga)), and its Intel half depended on the oneAPI FPGA support that Intel removed from compiler 2025.1 ([Intel oneAPI FPGA](https://intel.com/content/www/us/en/developer/tools/oneapi/fpga.html)). Allo, the successor to HeteroCL, is an active Python-embedded MLIR language, but code must be rewritten into its typed subset, and it has no tagged releases and no PyPI package ([Allo](https://github.com/cornell-zhang/allo)). hls4ml and FINN are mature but compile neural networks only; hls4ml 1.3.0 (March 2026) added a Libero backend for rad-hard PolarFire ([hls4ml releases](https://github.com/fastmachinelearning/hls4ml/releases)). LLM-assisted flows emit HLS C++ and still need synthesis and co-simulation loops; the LAAFD authors state that naive direct translation is unlikely to be efficient ([LAAFD](https://arxiv.org/html/2602.06085v1)). Underneath every route, HLS demands fixed or bounded sizes and rejects dynamic memory, recursion and system calls ([UG1399](https://docs.amd.com/r/en-US/ug1399-vitis-hls/Unsupported-C/C-Constructs)), which rules out `np.polyfit` inside loops, boolean masking with variable output length and every optimizer.

A perfect translator would still collide with the OpenTSx parity contract. Every runtime computes in IEEE 754 double precision: Rust episodes are `Vec<f64>` (`rust/tsx-runner/src/model.rs:77`), the Avro Episode carries `array<double>` (`opentsx-model/src/main/resources/schema-history/v2.0/Episode.avsc`), and the Rust operator modules contain no `f32`. Admission demands identical wire bytes, clean-operator agreement within `1e-12 * max(1, |expected|)`, pair cross-correlation within 5e-13, exact equality for stats, segments, SAX and DQ, and identical sketch bytes (SPEC:107-123); any change in output for any input must raise the operator and catalog versions (SPEC:55-57). FPGA kernels normally run in fixed point or float32, so **an FPGA kernel is a new operator version with its own tolerance class, not a faster copy of an existing one**. The repository already has the mechanism: the owner approved a relative 3e-12 bound for federated moments (TASK-020:506-511).

What remains possible is re-implementation of a bounded streaming subset from the algorithm specification, which is how the Rust port was done. Vendor IP covers the signal-processing core (FIR, FFT, windowing, correlation, cumulative sum) in the AMD AI Engine DSP library and in Microchip's CoreFFT, which is free with any Libero licence ([AIE DSP API](https://docs.amd.com/r/en-US/Vitis_Libraries/dsp/user_guide/L2/api-reference.html); [CoreFFT](https://www.microchip.com/en-us/products/fpgas-and-plds/ip-core-tools/corefft)). AMD stopped maintaining its programmable-logic data-analytics and quantitative-finance HLS libraries in 2025.2 ([Vitis Libraries](https://docs.amd.com/r/en-US/Vitis_Libraries/index.html)), and the research found no published FPGA implementation of DFA or Hurst estimation, ARIMA, event synchronization or STL. A survey of 46 HLS-versus-RTL comparisons puts HLS productivity at about six times hand RTL ([Tampere](https://trepo.tuni.fi/bitstream/10024/126643/1/Are_We_There_Yet.pdf)). That is the realistic gain on offer: faster hand-writing, not conversion.

## OpenTSx already holds the skeleton of a tiered operator library

The second framing is the better one, and the repository contains most of the machinery for it. AGENTS.md requires UI execution, library APIs, Wayang mappings and Rust execution to stay distinct and says a numerical kernel does not establish a deployed runtime binding (`AGENTS.md:117-120`). Measured that way, the frozen catalog `tsx-catalog/1` holds 16 operators (`systems/catalogs/tsx-catalog-1.yaml:1-18`), all mapped to Wayang Java operators. The Rust `tsx-runner` executes 15 of them in the isolated B2 profile and must reject `pair.es` (SPEC:368-369). **Only four** (decode, `dq.checks`, `convert.unit` and trailing `resample`) are reachable through `RustPlatform` (`opentsx-wayang/src/main/java/org/opentsx/wayang/rust/RustRollout.java:56`), and under signed, policy-checked admission the runner accepts pass-through only (`rust/tsx-runner/src/run_plan.rs:410-414`). The evidence behind the Rust track is strong: B2 passes all 57 shared numerical cases, and the track-parity test compared 2,160,000 values across 36 increments and 72 restarts with zero differences (TASK-020:434-451).

The three tiers map onto the repository's two tracks plus one new layer. Track A, native Wayang Java operators on JVM sites, is Tier 1; Track B, the same catalog in a small static Rust binary for low-capacity hardware, is Tier 2 (Concept 20:41-42). The "on-board computer" row in the track-selection table (Concept 20:869) refers to boats, gateways and substations; the repository never mentions satellites, orbit or radiation. Tier 3 has no analogue, and the German LabVIEW comparison states that timed loops, real time and FPGA are **not** OpenTSx's job (`docs/datamodel-2026/09-STUDIO-LABVIEW-STEUERPULT.md:130`). Two existing rules fit space directly. The federation goal, raw data stays at its site and only mergeable aggregates and signals leave it (Concept 20:34-35), is the space use case with a spacecraft as the site. The forwarder design for intermittent links, where "the link may be down for days; site retention must cover that gap" (Concept 20:404-407), is the pass-based downlink. Decision D-T1 chose a single non-JVM runtime because two edge runtimes double the parity work per operator (TASK-020:493; Concept 20:896); an FPGA tier is a third parity track and must stay small.

Wayang can host the library, within limits OpenTSx already works around. Wayang became an Apache top-level project in late 2025 and 1.1.1 (February 2026) is the latest release ([ASF](https://news.apache.org/foundation/entry/the-apache-software-foundation-announces-new-top-level-projects-3); [projects.apache.org](https://projects.apache.org/json/projects/wayang.json)); OpenTSx pins 1.1.1 (`pom.xml:60`). A platform is a `Platform` singleton plus execution operators, `Mapping`s, channels, channel conversions, an executor and a plugin, with cost formulas in a defaults file ([Platform.java](https://github.com/apache/wayang/blob/main/wayang-commons/wayang-core/src/main/java/org/apache/wayang/core/platform/Platform.java)). A platform runs exactly the operators it has mappings for, and `addTargetPlatform` pins an operator to a platform ([OperatorBase.java](https://github.com/apache/wayang/blob/main/wayang-commons/wayang-core/src/main/java/org/apache/wayang/core/plan/wayangplan/OperatorBase.java)). The TensorFlow plugin shows an accelerator platform declaring the host platform it needs ([TensorflowPlugin.java](https://github.com/apache/wayang/blob/main/wayang-platforms/wayang-tensorflow/src/main/java/org/apache/wayang/tensorflow/plugin/TensorflowPlugin.java)), and the 2026 Ollama executor shows the minimal pattern for a platform whose work runs in a remote service ([OllamaExecutor.java](https://github.com/apache/wayang/blob/main/wayang-platforms/wayang-semantic/src/main/java/org/apache/wayang/semantic/execution/OllamaExecutor.java)). The limits are real: no streaming in the Java platform and no federation (Concept 20:114-115), "adding a platform" documentation pages that contain only titles ([Wayang docs](https://github.com/apache/wayang/tree/main/wayang-docs/src/main/resources/extending_wayang/adding_platform)), a small contributor base, and **no GPU or FPGA platform for Wayang or its Rheem predecessor**. No published system places one logical operator across JVM, native-CPU and FPGA implementations under one cost-based optimizer. The nearest prior art, Spark RAPIDS, Gluten with Velox cuDF, and Presto on GPUs, swaps in accelerated operators where they exist and falls back to the CPU elsewhere ([Gluten 1.8.0](https://github.com/apache/gluten/releases/tag/v1.8.0-rc0); [Presto on GPUs](https://arxiv.org/pdf/2606.24647)), which is what a missing Wayang mapping already does.

The case for containers deserves a fair hearing before it is set aside. Containers do fly: Unibap SpaceCloud uplinks only app layers on a shared base image, which compresses simple apps to tens of kilobytes ([Flordal et al.](https://zenodo.org/record/5522872/files/12.02_OBDP2021_Flordal.pdf?download=1)), and ESA added apps to Phi-sat-2 after launch ([ESA](https://www.esa.int/Applications/Observing_the_Earth/FutureEO/Phsat-2/Phsat-2_gets_two_new_AI_apps)). Against that, flown runtimes are tight (the CogniSAT-6 environment was listed as Python 2.7 with about 50 MB of RAM ([JPL](https://ai.jpl.nasa.gov/public/documents/presentations/zilberstein-fswws-2025.pdf))), validation dominates (the Phi-sat-2 team ported a Python pipeline to Java and accepted a mean absolute error of 6e-4 against the Python reference ([arXiv 2610.11735](https://arxiv.org/pdf/2610.11735))), and Wayang's Python path ships UDFs as base64 cloudpickle blobs run by a spawned `python3` worker per call ([serializer.py](https://github.com/apache/wayang/blob/main/python/src/pywy/core/serializer.py); [PythonProcessCaller.java](https://github.com/apache/wayang/blob/main/wayang-api/wayang-api-python/src/main/java/org/apache/wayang/api/python/executor/PythonProcessCaller.java)). A pickled UDF gives the optimizer no operator identity to map to Rust or FPGA and would put executable code on the uplink; OpenTSx already rejected `wayang-api-json` for compiling source from requests and requires plans that "name operator ids, never code" (Concept 20:333-334, 619). A signed plan of a few kilobytes crosses a hundreds-of-kbps uplink in under a second. The repository's planned answer for user logic, WASM operators under wasmtime with fuel and memory caps (Concept 20:214; TASK-020 B5), is the right sandbox for experiments that have not earned catalog status; it is planned, not built.

## Raw sensor rates exceed a day of S-band downlink by 460 times

Downlink capacity is set by geometry before radios. A LEO satellite is visible to a ground station for about ten minutes on four to five good passes per day, and stations support Gbps downlink but only hundreds of kbps uplink ([L2D2, SIGCOMM 2021](https://conferences.sigcomm.org/sigcomm/2021/files/papers/3452296.3472932.pdf)). Taking 3,000 seconds per station per day as an upper bound before protocol overhead gives these daily volumes.

| Band and rate | Daily volume, one station | Rate source |
|---|---|---|
| UHF, 9.6 kbps | 3.6 MB | [MDPI review](https://mdpi.com/2078-2489/11/5/258) |
| S-band, 1 Mbps | 375 MB | [NASA NTRS](https://ntrs.nasa.gov/api/citations/20160001365/downloads/20160001365.pdf) |
| X-band, 100 Mbps | 37.5 GB | [Frontiers 2024](https://www.frontiersin.org/articles/10.3389/frcmn.2024.1356484/pdf) |
| X-band, 500 Mbps | 187.5 GB | [Frontiers 2024](https://www.frontiersin.org/articles/10.3389/frcmn.2024.1356484/pdf) |
| Ka-band, 2.2 Gbps | 825 GB | [KSAT white paper](https://www.ksat.no/globalassets/ksat/documents/ksat_white_paper.pdf) |

Set an illustrative housekeeping-class feed against those numbers: 1,000 channels sampled at 1 kHz with 16-bit samples. This is a scale assumption, not a cited mission. OpenTSx's own wire format makes things worse before it makes them better, because Episode values are Avro `array<double>` and each 2-byte sample becomes 8 bytes before compression.

| Stage of the same feed | Rate | Per day | Smallest single-station link that carries it |
|---|---|---|---|
| Raw 16-bit samples | 2 MB/s | 172.8 GB | X-band at 500 Mbps |
| Same samples as f64 Episode values, before zstd | 8 MB/s | 691 GB | Ka-band at 2.2 Gbps |
| `resample` to 1 Hz, MEAN, MIN and MAX as f64 | 24 KB/s | 2.07 GB | X-band at 100 Mbps |
| Per-minute window statistics, 100 to 200 bytes per channel and window | 1.7 to 3.3 KB/s | 144 to 288 MB | S-band at 1 Mbps |
| `dq.result` signals on violations only | event-driven | KB to MB (assumed) | UHF |

**Per-minute statistics cut the volume by 600 to 1,200 times** and turn an X-band problem into an S-band one, and the reducers that achieve it (`resample`, `stats.welford-ddsketch`, `dq.result`) already exist in the catalog. The 200-byte figure is an assumption: the moments alone are seven f64 values, and a DDSketch can grow to 4,096 bins. Two further numbers decide where those reducers run. The Track B budget is one core at 10,000 values per second, still unmeasured (Concept 20:390-402); the illustrative feed delivers 1,000,000 values per second, **25 times what four Cortex-A53 cores could handle at that budget**, so raw-rate reduction belongs in FPGA logic. High-rate instruments leave no choice at all: one SpaceFibre lane at its 5 Gbit/s user rate ([ESA SpaceFibre](https://ecss.nl/standard/ecss-e-st-50-11c-spacefibre-very-high-speed-serial-link/)) fills 1 GiB of memory in under two seconds, so a 4 to 16 GiB ring buffer on a smallsat board holds about 7 to 27 seconds of such data.

Uplink economics point the same way. A signed plan of a few kilobytes with a 64-byte Ed25519 signature ([RFC 8032](https://www.rfc-editor.org/rfc/rfc8032)) uplinks in under a second. HYPSO-1's partial and full bitstreams of 2.85 MB and 5.84 MB ([Eine et al., IAC 2024](https://rogerbi.folk.ntnu.no/publ/2024_Reconfig_IAC_paper.pdf)) take about 89 and 182 seconds at 256 kbps, and a full XQRKU060 bitstream of about 24.1 MB ([UG570](https://docs.amd.com/r/en-US/ug570-ultrascale-configuration/Device-Resources-and-Configuration-Bitstream-Lengths)) takes about 32 minutes at 100 kbps. **Kernels should take their parameters from registers so that most plan changes need no new bitstream.** Flight results confirm the system-level payoff: HPE's ISS computer processed 1.8 GB onboard in six minutes instead of a 12.2-hour downlink ([HPE](https://www.businesswire.com/news/home/20220404005739/en)); HYPSO-1 compresses hyperspectral cubes on its FPGA in about 184 ms against 398 s in software ([Eine et al.](https://rogerbi.folk.ntnu.no/publ/2024_Reconfig_IAC_paper.pdf)); and orbital edge computing work reports a more than 24-fold reduction in ground infrastructure versus bent-pipe designs ([Denby and Lucia, ASPLOS 2020](https://abstract.ece.cmu.edu/pubs/oec-asplos2020.pdf)). For telemetry time series, flown evidence reports detector accuracy, not reduction ratios or FPGA resources, so the ratios above remain design estimates.

## Each operator goes to the lowest tier that keeps its contract

The placement rule that falls out of the contract is simple. An operator belongs on the FPGA only if it reduces raw-rate data and its hardware form can be checked exactly. It belongs on the onboard CPU if it needs f64 finishing, keyed state, Avro or JSON framing, or sees only reduced data. It stays on the ground if it needs whole-series statistics, iterative fitting, history or surrogates. The code structure supports this split: per-sample checks, affine conversion, window accumulators, FIFOs, hysteresis state machines and bounded lagged correlation have fixed-size state; spectral, sketch, SAX and alignment operators need buffers, logarithms or FFT IP; fitting, decomposition, surrogate and history operators belong on a CPU.

The design device that makes Tier 3 affordable is a **partial and finish split**: the FPGA emits exact integer partials, and the Rust runner finishes in f64. Raw ADC samples are integers, so integer sums, sums of squares, counts, minima and maxima are exact. The Rust `resample` accumulator is `{start, sum, count, min, max, last}` (`rust/tsx-runner/src/operators.rs:89-121`); with integer-valued input whose sum stays below 2^53 its f64 sum is exact, so an exact integer partial followed by one division in Rust reproduces the same mean. Plans that apply `convert.unit` before `resample` can be rewritten to apply the affine map after reduction. The rewrite holds for MEAN, MIN, MAX and LAST when the factor is positive (MIN and MAX swap when it is negative) and changes results only through rounding order, which the 15 clean-operator vectors must bound at their 1e-12 tolerance. `dq.checks` thresholds convert into raw counts, with boundary vectors deciding how a sample exactly on a threshold rounds. The moment part of `stats.welford-ddsketch` is different: the contract requires exact equality with the Java Welford sequence (SPEC:107-123), and exact integer moments are more accurate but not bit-identical, so **FPGA moments must ship as a new stats operator version**. For 16-bit samples, sums of squares stay exactly representable in f64 for windows up to about two million samples, which covers per-minute windows at 1 kHz with a wide margin.

Three consequences follow for OpenTSx. A portable Tier 2 can rely only on a Linux container, a local writable filesystem, a downlink staging call and an accelerator, so any Kafka-protocol log must sit on that filesystem. On hosted platforms the operator owns the downlink, so sealed log chunks leave as staged files that must fit platform limits such as SpaceCloud's 500 KB output cap. And hosted platforms schedule apps in windows (ten minutes per wake-up in the SpaceCloud demonstration), which suits the runner's bounded increments and checkpoints but not an always-on broker.

### Onboard broker: no Kafka-protocol log has flown, and S3 belongs on the ground

No Kafka-protocol broker has documented flight heritage. The OpenTSx rules narrow the field: producers publish only to Apache Kafka brokers or the KafScale Proxy (`AGENTS.md:72-74`), and every producer runs with `enable.idempotence=false`, `acks=all` and one request in flight (`opentsx-kafka-v2/src/main/java/org/opentsx/kafka/KafScaleClients.java:16-62`; `rust/tsx-runner/src/broker.rs:100-110`), a contract that already tolerates a broker without idempotence or transactions. KafScale itself depends on etcd and S3. Its in-memory mode removes the object store but not etcd: the Wayang-Rust profile sets `KAFSCALE_USE_MEMORY_S3: "1"` (`docker-compose.wayang-rust.yml:64`) and still sets `KAFSCALE_ETCD_ENDPOINTS` (`docker-compose.wayang-rust.yml:69`), while the durable profile points KafScale at a MinIO endpoint and bucket (`docker-compose.kafscale.yml:50-56`). **KafScale can therefore start onboard without a real S3, but in that mode its log is volatile and etcd remains a dependency.** The only footprint figure is 32 to 50 MiB RSS for one in-memory broker on ARM64 macOS (`REPORT.md:354-418`), not Linux on flight hardware.

The services evidence settles the S3 question. A local S3-compatible store plus etcd per satellite fits only on multi-gigabyte nodes, doubles fsync traffic on flash, risks metadata corruption on brownout, and still has to downlink every byte through the operator's file path; MinIO, the store behind the durable KafScale profile, recommends 32 GiB per host and its community edition was archived in February 2026 ([MinIO checklist](https://min.io/docs/minio/linux/operations/checklists/hardware.html); [It's FOSS](https://itsfoss.com/news/minio-moves-away-from-open-source/)). Ground S3 over a relay needs an app-level IP route that no provider documents. **The lower-risk design is a non-S3 local log onboard whose sealed segments are downlinked into ground S3 and imported into ground KafScale.** The recommendation is a bake-off on aarch64 Linux between Apache Kafka KRaft on local segments (rule-compliant, no S3, no etcd) and KafScale in memory-S3 mode backed by a durable chunk spool (rule-compliant, same family as ground, etcd onboard), with Tansu/Nisshi measured as the small-board alternative that would need a rule amendment. The gate is the existing `opentsx-kafscale-conformance` suite plus repeated power cuts. Durability needs one deliberate change on a single node. OpenTSx writes its checkpoint only after all earlier deliveries are acknowledged (Concept 20:587-594), and the raw ring in DDR does not survive a power cut, so an acknowledged record that the log then loses is gone for good. Kafka's default of no application fsync, which relies on replicas that a single onboard node does not have, therefore has to be replaced by explicit flush settings on the onboard log; with KafScale's memory-S3 mode, the runner's checkpoint has to wait for the durable chunk seal rather than for the broker acknowledgment.

### Connecting the tiers: sealed offset chunks over the link, DMA rings below it

Between Tier 2 and Tier 1, broker replication does not fit. MirrorMaker 2's offset translation is lossy ([Red Hat](https://docs.redhat.com/en/documentation/red_hat_streams_for_apache_kafka/3.1/html/disaster_recovery_using_mirrormaker_2/con-mm2-offset-translation-str)) and its producer defaults to idempotence, which KafScale cannot serve; Confluent Cluster Linking and Redpanda Shadowing need the same vendor on both sides ([Confluent](https://docs.confluent.io/platform/current/multi-dc-deployments/cluster-linking/faqs-cp.html); [Redpanda](https://docs.redpanda.com/current/manage/disaster-recovery/shadowing/overview/)); all three assume TCP and simply lag while the link is down. Airbus, connecting polar stations over GEO links, also avoided a stretched cluster and added deduplication ([Kafka Summit](https://www.kafka-summit.org/sessions/kafka-in-space)). The recommended bridge reuses OpenTSx's own at-least-once design. An onboard downlink agent consumes each topic partition by manual assignment, seals immutable chunks `[startOffset, endOffset)` named by spacecraft, topic, partition and offsets, the same key scheme the Confluent S3 sink uses for exactly-once export ([Confluent](https://docs.confluent.io/kafka-connectors/s3-sink/current/overview.html)), and signs each chunk with SHA-256 and Ed25519. On missions that own their bus, chunks travel as CFDP Class 2 files with ACK and NAK retransmission ([Yamcs CFDP](https://docs.yamcs.org/yamcs-server-manual/services/instance/cfdp/)) or as BPv7 bundles with BPSec where relays sit in the path ([RFC 9171](https://www.rfc-editor.org/rfc/rfc9171); [RFC 9172](https://www.rfc-editor.org/rfc/rfc9172)); DTN is operational on NASA's PACE mission ([NASA](https://www.nasa.gov/technology/space-comms/dtn-overview-benefits-successstories-learningresources)). On hosted platforms, chunks leave through the platform's staging call. Either way they land in ground S3, and a ground ingester produces them into KafScale through `KafScaleClients.producer` with headers carrying the source coordinates, dropping any offset at or below a per-partition high-water mark. OpenTSx's deterministic derived episode ids (Concept 20:596) give a second deduplication key. The onboard agent advances its downlinked-through offset only after ground acknowledgment, and onboard retention must exceed the reduced production rate times the longest gap between acknowledged passes. Small, urgent topics such as `dq.result` go first in every pass.

|---|---|---|
| CCSDS packets in TM, TC, AOS or USLP frames with SDLS | hop authentication, encryption and anti-replay ([CCSDS 355.0-B-2](https://public.ccsds.org/Pubs/355x0b2.pdf)) | Underlay on own-bus missions |
| CFDP Class 2 | acknowledged file delivery | Carry sealed chunks on own-bus missions |
| BPv7 with BPSec (HDTN, uD3TN, ION) | PACE operational; HDTN on ISS ([NTRS](https://ntrs.nasa.gov/api/citations/20240007078/downloads/HDTN_ISS_Testing_2024.pdf)); uD3TN on OPS-SAT ([arXiv](https://arxiv.org/pdf/2407.17166)) | Carry chunks across relays |

Between Tier 2 and Tier 3 the boundary is shared memory, not Kafka. The standard Zynq UltraScale+ ring is an AXI DMA in scatter-gather cyclic mode writing into reserved DDR ([PG021](https://docs.amd.com/r/en-US/pg021_axi_dma/MM2S_DMACR-MM2S-DMA-Control-Register-Offset-00h)), shared with Linux either through I/O-coherent HPC ports with a `dma-coherent` device-tree node ([AMD wiki](https://xilinx-wiki.atlassian.net/wiki/spaces/A/pages/18842098/Zynq+UltraScale+MPSoC+Cache+Coherency)) or through non-cached buffers from u-dma-buf ([udmabuf](https://github.com/ikwzm/udmabuf)). The flown host-control pattern is HYPSO-1's: Linux FPGA Manager loads a bitstream plus a device-tree overlay that instantiates UIO drivers, measured at 61 ms for a partial bitstream, 112 ms for a full one and 253 ms with the overlay, operational since March 2024, with software fallback when no matching design is loaded ([Eine et al.](https://rogerbi.folk.ntnu.no/publ/2024_Reconfig_IAC_paper.pdf)). On AMD parts, dfx-mgr adds accelerator packages and a socket that containers can use ([dfx-mgr](https://github.com/Xilinx/dfx-mgr/blob/master/README.md)); on PolarFire SoC, Microchip's examples use UIO plus u-dma-buf ([Microchip](https://github.com/polarfire-soc/polarfire-soc-linux-examples/blob/master/dma/README.md)). Kubernetes FPGA device plugins target PCIe data-center cards only. In this design the runner is the only component that frames Avro, computes xxHash64 series ids and partitions with murmur2; the FPGA never touches transport, which matches the repository's separation of numerical vectors from wire and identity suites (SPEC:178-180).

## Two new Wayang platforms compile signed plans per contact window

**Split every three-tier plan at the space link.** Wayang optimizes and executes one bounded job at a time, and whether its cross-platform executor tolerates stages that wait hours for a pass is unverified, so no ground job should wait for orbit. A bounded ground job compiles the onboard part into an uplink bundle and finishes. The onboard runner executes that bundle as successive bounded increments with local checkpoints, the existing continuous local profile (`docs/devguide/integration/wayang-rust-continuous.md:8-48`). Later bounded ground jobs consume the downlinked result topics. The existing two-phase handoff maps cleanly: HTTP `prepare` becomes uplink plus signature verification, `activate` becomes scheduled activation inside the plan's validity window (`issued <= now < expires`, `docs/devguide/integration/rust-runner-b1.md:93-95`), and `GET /v1/capabilities` becomes a capability report in housekeeping telemetry from which the ground generates mappings. The satellite becomes an OpenTSx site: its topics follow `TopicLayout` (`tsx.<domain>.<kind>.v2`) with the spacecraft in the domain, and contract C9, each series id belongs to exactly one site (Concept 20:226-236), becomes each series id belongs to exactly one spacecraft.

| Element | Tier 1, ground | Tier 2, onboard CPU | Tier 3, FPGA |
|---|---|---|---|
| Wayang platform | `JavaPlatform` with `TsxJavaPlugin`; `RustPlatform` as the ground twin | `OnboardPlatform` (new, config name `onboard`) | `FpgaPlatform` (new, config name `fpga`) |
| Plugin's required platforms | Java | Java, Onboard | Java, Onboard, FPGA, following the TensorFlow plugin pattern |
| Mappings | existing `Tsx*` operators | signed-B2 operator set, generated from the catalog and the downlinked capability report | kernel-pack and partial operators only; a missing mapping means "not on FPGA" |
| Channels | Collection and Stream; `TopicChannel` at boundaries | `TopicChannel`: reusable, breakpoint-suitable | `RingChannel`: neither reusable nor breakpoint-suitable |
| Conversions | Collection to and from `TopicChannel` via `TsxTopicSource` and `TsxTopicSink` | `TopicChannel` to and from onboard stages | onboard stages to and from `RingChannel` only; no Collection to `RingChannel` path exists |
| Executor | Java executor; `RustExecutor` over HTTP | compiles a complete stage into `opentsx.runner-plan.v1`, signs it with Ed25519, queues it for uplink, returns on queue acceptance (pattern: `OllamaExecutor`) | adds kernel bindings (kernel id, bitstream hash, slot, register values) to the same signed bundle |
| Cost and limits | today's placeholders, to be calibrated | load templates per operator; `getInitializeMillis` as time to next uplink; `.limit` keys for 1,024 series and 1,000,000 samples | `.limit` keys per kernel slot and ring size; energy per millisecond |
| First release | default | pinned with `addTargetPlatform` | pinned with `addTargetPlatform` |

Cost models need honesty first. Rust costs default to one millisecond per unit and every Java TSX load estimator reuses one formula copied from Wayang's Kafka source (`opentsx-wayang/src/main/resources/wayang-tsx-defaults.properties:1-40`; Concept 20:428-429), so the first release pins operators. Calibration then uses Wayang's own machinery: execution logs and `GeneticOptimizerApp` to learn `*.load.template` parameters ([cost-profiling guide](https://github.com/apache/wayang/blob/main/guides/cost-profiling.md)); `.limit.<slot>` keys that filter an execution operator out when estimated cardinality exceeds capacity ([ExecutionOperator.java](https://github.com/apache/wayang/blob/main/wayang-commons/wayang-core/src/main/java/org/apache/wayang/core/plan/wayangplan/ExecutionOperator.java)); and a custom `EstimatableCost` set through `Configuration.setCostModel` for contact windows, downlink bytes and energy ([Configuration.java](https://github.com/apache/wayang/blob/main/wayang-commons/wayang-core/src/main/java/org/apache/wayang/core/api/Configuration.java)). Output-cardinality estimators already express data reduction, which is what makes onboard placement win once costs are real. `explain()` should say why an operator did not land on the FPGA: no mapping, limit exceeded, or cost.

Wayang's own Kafka path stays out of this design. The upstream `KafkaTopicSink` builds a producer whose default properties **do not set `enable.idempotence`** ([KafkaTopicSink.java](https://github.com/apache/wayang/blob/main/wayang-commons/wayang-basic/src/main/java/org/apache/wayang/basic/operators/KafkaTopicSink.java)); Kafka clients turn idempotence on by default when no conflicting settings are given ([Kafka producer configs](https://kafka.apache.org/41/configuration/producer-configs/)), so the producer would request an `InitProducerId` that KafScale does not implement. The upstream `wayang-java` module also ships a `wayang-kafka-defaults.properties` file with environment-specific connection defaults. The source side is String-only with a single 15-second poll ([JavaKafkaTopicSource.java](https://github.com/apache/wayang/blob/main/wayang-platforms/wayang-java/src/main/java/org/apache/wayang/java/operators/JavaKafkaTopicSource.java)). OpenTSx already avoids all three by using `TsxTopicSource` and `TsxTopicSink` over `KafScaleClients` and loading only needed mappings (Concept 20:128-143, 276-282). Because OpenTSx depends on `wayang-java`, that properties file is on its classpath: add a test that asserts no property from it reaches an OpenTSx client.

### One contract per operator, shared by Java, Rust and FPGA

The contract extends the processor descriptions OpenTSx already ships (`systems/processors/*.yaml`, schema `docs/datamodel-2026/schemas/opentsx.processor.v1.schema.json:102-130`) rather than inventing a new registry. Prior art supports each field: Substrait separates function identity from options ([Substrait](https://substrait.io/extensions/)) and ONNX versions operator sets and ships shared backend tests ([ONNX](https://onnx.ai/onnx/repo-docs/Versioning.html)).

| Contract field | OpenTSx today | Addition for three tiers |
|---|---|---|
| Identity and version | catalog ids; any output change raises operator and catalog version (SPEC:55-57) | FPGA variants that change output are new versions; partial and finish operators are new ids whose composition must pass the parent operator's vectors |
| Ports and record types | `series`, `stats`, `vector`, `events`; `xy` and `model` never on topics (SPEC:62-71) | `raw` ring frames, allowed only between Tier 3 and Tier 2 and never on topics |
| Parameters | per-processor parameter lists | each parameter marked `register` or `synthesis`; thresholds also stated in raw counts |
| Numerics and tolerance | f64 everywhere; 1e-12, 5e-13 or exact (SPEC:107-123) | `numeric` per runtime (f64, exact integer, fixed Qm.n, f32) and a `toleranceClass`, approved like the 3e-12 moments bound |
| State | `none`, `keyed`, `windowed` on the epoch grid; state only in checkpoints (SPEC:83-91); Java and Rust formats not interchangeable (SPEC:419) | FPGA kernels hold only windowed state flushed at window ends; checkpoint cuts align to window ends; keyed state stays on Tier 2 |
| Vectors | JSON vectors and generators (`tools/java_operator_vectors.py`) | raw-ingest vectors, fixed-point vectors from a bit-accurate model, a cocotb run in CI |
| Runtimes block | `runtimes.wayang`, `runtimes.rust`; schema also allows `workbench`, `java`, `python`, `go`, `processor` | `runtimes.fpga` with kernel id, board family, bitstream hash, slot and resource report |
| Capacity | B2 ceilings of 1,024 series and 1,000,000 samples; `pair.xcorr` product limit | per-kernel channel and window limits, exported as Wayang `.limit` keys |
| Admission | EdDSA plans pinned to site, catalog and driver key; refusals `plan.site`, `plan.catalog`, `plan.signature`, `plan.policy`, `plan.busy` (`rust/tsx-runner/src/run_plan.rs:35-44`) | spacecraft id, monotonic plan sequence, validity window, catalog version and bitstream hashes inside the signed payload; key rotation |

### Kernel ABI, packaging and radiation

Each kernel takes an AXI4-Stream of raw samples with channel id and sequence in the side-band, reads its parameters from AXI-Lite registers, and writes fixed-layout window records into a result ring in ECC DDR. A static shell holds the sensor front end, the cyclic DMA writer, ring index registers and the scrubber interface; because a cyclic DMA needs a reset once stopped, the writer must stay in the static region while kernels change. Kernels ship as dfx-mgr-style packages (bitstream, overlay, metadata) extended with the OpenTSx operator id, version, vector-set hash and an Ed25519 signature. AMD UltraScale and UltraScale+ RSA bitstream authentication cannot be combined with partial reconfiguration or compression ([UG570](https://docs.amd.com/r/en-US/ug570-ultrascale-configuration/RSA-Authentication)), so on those parts the runner or supervisor verifies the Ed25519 signature before writing the bitstream, and the first release uses full bitstreams with a fixed kernel pack, as HYPSO-1 chose for operational simplicity. The ring lives in ECC DDR rather than block RAM, so it survives reconfiguration; ring head and tail indices with sequence numbers go into the runner's checkpoint so that a processor hang and watchdog reboot resume without losing position; and a scrubber correction is treated as a signal to recompute the current window.

## Test workloads on the ground before upload

The question was who offers a demo environment for testing workloads before they ship. This report reads that as pre-flight testing: environments in which Tier 2 operators and Tier 3 kernels are exercised on the ground before they are uplinked to orbit. **No platform vendor offers a free, public, flight-identical emulator of its onboard environment.** Two open-source environments reproduce a host-service layer on a laptop. The Azure Orbital Space SDK's Virtual Test Harness runs payload apps "the exact same way in a test environment as they would on orbit" on Kubernetes and Dapr, with data generators and plugins, and can integrate hardware for higher fidelity ([about-space-sdk.md](https://github.com/microsoft/azure-orbital-space-sdk/blob/main/docs/overview/about-space-sdk.md)); its last commit on main is dated 20 March 2025, so it is a frozen reference rather than a supported product ([commits](https://github.com/microsoft/azure-orbital-space-sdk/commits/main)). ESA's NanoSat MO Framework ships a simulator aligned with OPS-SAT that runs NMF apps without satellite hardware ([NMF docs](https://nanosat-mo-framework.readthedocs.io/en/latest/simulator/simulator.html)). Two vendors give access to flight-equivalent silicon. KP Labs' Smart Mission Lab sells remote access to real Leopard, Antelope and Lion DPUs, including FPGA-accelerated processing and power and fault-tolerance metrics, within two working days ([KP Labs](https://www.kplabs.space/news/smart-mission-lab---a-new-era-in-space-technology-validation)). Unibap sells Application Development Systems with the same CPU, GPU and I/O as its iX5 and iX10 flight units, price on request ([satsearch](https://satsearch.co/products/unibap-application-development-systems)). Everything else is bound to a contract: Loft's virtual test bench ([Loft](https://www.loftorbital.com/post/virtualmission)), Spire's QEMU-runnable Yocto payload image plus customer-bought Jetson hardware ([Spire](https://developers.spire.com/space-services-user-guide/)), and Antaris TrueTwin with software- and hardware-in-the-loop ([SatNow](https://www.satnow.com/news/details/4361-antaris-showcases-satos-software-platform-for-flexible-spacecraft-development)). ESA's OPS-SAT PRETTY shares hardware, emulators and software environments with registered experimenters at no cost for European entities, with C and C++ as the baseline language ([OPS-SAT FAQ](https://opssat.esa.int/faq)).

The open-source tools for the spacecraft and the link are mature where they model flight software and weak where they model contact windows. NASA's NOS3 couples cFS with the 42 dynamics simulator and COSMOS, F Prime, YAMCS or AIT ground software ([NTRS 20250001688](https://ntrs.nasa.gov/citations/20250001688)), which makes it a candidate for exercising the command path that carries signed plans, but it is built around cFS apps, not containers or Kafka. JPL's F Prime is maintained, with a breaking 4.0.0 release in August 2025 and a pip-installed Python ground data system ([F Prime](https://fprime.jpl.nasa.gov/news/2025/08/07/f-prime-v400-released)). OpenC3 COSMOS, the ground command and control used with NOS3, is on its 7.x line, and its security record argues for pinned, current versions in any test bench that touches signing keys: CVE-2025-68271 allowed remote code execution through the JSON-RPC API in 5.0.0 through 6.10.1, fixed in 6.10.2 ([NVD](https://nvd.nist.gov/vuln/detail/cve-2025-68271)), and two further CVEs published in May 2026 affect 7.0.0 release candidates before rc3 ([exploit-intel](https://exploit-intel.com/vuln/CVE-2026-42085)). Renode boots an unmodified Linux BSP on a simulated PolarFire SoC Icicle Kit, co-simulates RTL with Verilator and runs fault-injection scenarios in CI ([Microchip](https://www.microchip.com/en-us/about/media-center/blog/2022/microchip-risc-v-platforms-in-antmicro-open-source-renode); [Antmicro](https://antmicro.com/blog/2024/02/developing-and-testing-space-systems-with-renode)). LEO network emulators such as Celestial, StarryNet and OpenSN are research prototypes; a 2026 comparison against real Starlink measurements found that none "comes close" and none models contact windows or handover outages explicitly ([arXiv 2604.04498](https://arxiv.org/html/2604.04498v1)). Celestial fits Tier 2 structurally, because every satellite and ground station is a full Linux microVM ([Celestial](https://github.com/OpenFogStack/celestial)), but for one satellite and a handful of stations, Linux `tc netem` driven by a pass schedule from an orbit propagator is simpler and easier to control.

For Tier 3, commercial evaluation boards are functional stand-ins, not bitstream twins. The VCK190 carries production XCVC1902 silicon and lists at $13,195 ([AMD](https://www.amd.com/en/products/adaptive-socs-and-fpgas/evaluation-boards/vck190.html)); a 2026 heavy-ion study used it as the commercial counterpart of XQRVC1902 ([Star-Dundee](https://www.star-dundee.com/wp-content/star_uploads/2026/03/AGV_Characterisation-of-AMD-Versal-FPGA-Transceivers-Under-Heavy-Ion-Radiation.pdf)), whose Class Y package is pin-compatible with the commercial VC1902 ([StorageReview](https://www.storagereview.com/news/amd-versal-ai-core-xqrvc1902-space-grade-lidless-class-y-samples)). The obvious XQRKU060 stand-in is wrong: the KCU105 carries a KU040, not a KU060 ([XAPP1230](https://download.amd.com/docnav/documents/XAPP1230.pdf)). Microchip's RT PolarFire development kit carries a prototype RTPF500 die at $22,524 ([DigiKey](https://www.digikey.com/en/products/detail/microchip-technology/RTPF-DEV-KIT-CB-1/17631064)), while the commercial PolarFire SoC Icicle Kit, launched at $489 ([Crowd Supply](https://www.crowdsupply.com/microchip/polarfire-soc-icicle-kit/crowdfunding)), is the cheap stand-in for the RISC-V and fabric combination; NanoXplore's NG-ULTRA eval kit has no public price. No source confirms that a bitstream built for a commercial board runs unchanged on its space-grade counterpart, so place and route, timing closure and scrubbing integration must be redone for the flight part. Configuration upsets can be injected without a beam: the UltraScale SEM IP accepts injection commands in its testing modes and Versal XilSEM exposes error-injection calls ([PG187](https://docs.amd.com/r/en-US/pg187-ultrascale-sem/Mode); [UG643](https://docs.amd.com/r/2023.1-English/oslib_rm/XSem_CmdNpiInjectError)). Flash-based PolarFire parts have no equivalent configuration injection, so their user-logic upsets need RTL-level injection. Real cross-sections, latch-up and functional-interrupt rates still need a beam: Texas A&M bills with an eight-hour minimum ([TAMU](https://cyclotron.tamu.edu/ref/)), PSI's proton facility serves ESA programs first ([PSI](https://www.psi.ch/en/pif)), and the EU RADNEXT program offered free beam time through competitive calls, with its 2026 status unconfirmed ([RADNEXT](https://indico.cern.ch/event/1353707/contributions/5884321/attachments/2876587/5057759/2024.06.13_GB-RADNEXT_Vortrag_GD_V1.0.pdf)).

Several gaps remain open after this research. No measured footprint exists for any Kafka-protocol broker, etcd or object store on a flight-class ARM64 board, and no write-amplification data exists for flash. The research found no published FPGA implementation of DFA, ARIMA, event synchronization or STL, no flown hls4ml or FINN design, and no FPGA resource, power or latency figures for any flown telemetry detector. Typical smallsat orbit-average power for payload computing was not sourced, so duty-cycling needs are unquantified. Per-app RAM and storage quotas are unpublished for every hosted platform, as are the APIs of Loft Cockpit, Spire's Data Pipeline and SpaceCloud storage. Authenticated partial reconfiguration on Versal and RT PolarFire was not confirmed, nor was SmartHLS support for RT PolarFire SoC part numbers. No vendor sandbox publishes a price, no source confirms bitstream portability between a commercial board and its space-grade counterpart, no development board for XQRVE2302 was identified, and whether the Smart Mission Lab accepts user bitstreams is not stated. Inside OpenTSx, no raw-ingest contract exists, the Python package's Avro decoding was never checked against the wire vectors, and no cost model has been measured.

## Conclusion: seven evidence-gated phases from ground twin to orbit

The question "can the Python code become FPGA code" turns out to be the wrong unit of portability. What moves between ground JVM, onboard Rust and FPGA fabric is an operator contract plus its vectors; the Python package's role becomes oracle and research tool, never payload. The partial and finish split is what keeps a third runtime affordable, because it shrinks the FPGA's parity surface to integer kernels that can be checked bit for bit while f64 semantics stay where the contract needs them. Wayang's role is likewise narrower than "runtime everywhere": it is the ground-side compiler, placement explainer and signer, and the satellite is simply an OpenTSx site with an extreme version of the intermittent link the federation design already anticipated. S3 follows the same logic and stays on the ground, where downlinked chunks land and ground KafScale reads them.

Two implications go beyond OpenTSx. A cost-based optimizer that places one logical operator across JVM, native and FPGA implementations, with contact windows and downlink bytes in the cost model, does not exist in the published literature, so the work has research value as well as product value. And every hosted-app platform found offers the same thin service set, which means an operator library that needs only a container, a local filesystem and a staging call can target all of them, while an S3- or etcd-dependent design can target none without bringing its own infrastructure. Because no vendor offers a public flight-identical emulator, the evidence for each tier has to come from rigs the team owns, with vendor environments used only for the final host-specific check. The roadmap below orders work so that each phase produces evidence before the next one spends money, mirroring the repository's own rule that the first deployment before Track B existed was "A everywhere" (Concept 20:872): the first space deployment before Tier 3 exists is Tier 2 only.
