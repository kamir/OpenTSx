This page gives the related-work study, the comparison and the claim check for the IEEE paper on OpenTSx, based on 188 candidate records (174 in clusters A to H, 14 in cluster I) and the code profile of OpenTSx; all sources were accessed on 2026-11-16.

Status: code facts refer to commit `548f316` of kamir/OpenTSx (2026-10-28). Statements about commercial products come from vendor documentation, blogs or press releases and are vendor claims unless another source is named.

Verification: candidate facts of high and medium relevance in clusters A to H were verified against primary sources on 2026-11-16, and every correction is applied in this report. Confirmed and corrected candidates per cluster: A 11 and 6, B 13 and 5, C 14 and 1, D 10 and 3, E 14 and 4, F 9 and 8, G 12 and 0, H 9 and 5; one candidate in H could not be verified (Google Cloud Timeseries Insights API). In total 125 candidates: 92 confirmed, 32 corrected, 1 unverifiable (working files `fix-tsms-distributed.json`, `fix-libraries-federation.json`, `fix-semantics-collectors.json`, `fix-commercial.json`). Confirmed candidates that only gained newer release data are counted as confirmed. Low-relevance entries were not re-verified; the only exception is the Uptake ownership note in G (confirmed). Cluster I was collected after that pass; facts in it that rest on search snippets only are marked "not verified".

## 1. Scope and method

### 1.1 Question

The owner's thesis reads: the abstraction of the time-series analysis domain in the OpenTSx domain model, plus the extension of data access to many raw-data collectors through Apache Wayang as a data federation layer, is a new evolutionary stage after Hadoop.TS [1].

The study answers four questions:

1. What did Hadoop.TS contribute in 2013, and what does OpenTSx implement today?
2. Which systems, libraries, standards and products abstract time series in a comparable way?
3. Which properties of OpenTSx are new as a combination, and which exist elsewhere?
4. Which parts of the thesis need an implementation or an evaluation before submission?

### 2.3 What distinguishes OpenTSx

The five distinguishing claims of the first draft were tested against the candidates of Section 5, the verification files and 20 checks of primary sources made on 2026-11-16. For each claim the test asked whether one checked system, standard or library already has the property. Code facts refer to commit `548f316`. Details, evidence and counterparts are in Section 8.

Result per claim:

1. **Episode as one unit for storage, exchange and replay: holds alone, in a narrowed form.** No checked counterpart defines one record that carries values, an optional quality byte per value, a summary with a stated merge rule and a provenance record with a parent link, and that is used unchanged for storage, exchange and replay (`opentsx-model/src/main/avro/Episode.avsc:5-22`; `opentsx-model/src/main/java/org/opentsx/model/Summaries.java:33-48`). Every part exists elsewhere: segments with value quality and value origin qualifiers in the AAS template ([IDTA 02008-1-1](https://industrialdigitaltwin.org/wp-content/uploads/2023/03/IDTA-02008-1-1_Submodel_TimeSeriesData.pdf)), per-point quality in [TimeseriesML 1.3](https://docs.ogc.org/is/15-042r6/15-042r6.pdf), flag variables and a `history` attribute in [NetCDF-CF 1.11](https://cfconventions.org/Data/cf-conventions/cf-conventions-1.11/cf-conventions.html), chunks with count, min, max and sum statistics in [Apache TsFile](https://github.com/apache/tsfile), and segments moved from edge to cloud in [ModelarDB](https://www.vldb.org/pvldb/vol18/p5247-jensen.pdf). The claim is therefore a data-model design claim, not a new mechanism. It must also state its limits: the schema defines only quality 0 as ok (`Episode.avsc:16`), the summary ignores the quality byte (`Summaries.java:11`), and the origin class is a label, not a field (`opentsx-market/src/main/java/org/opentsx/market/EpisodeMapper.java:42`).
2. **Content-derived series id and byte-identical Java and Python encoding: holds only as part of the combination.** The hashed id is refuted as a distinction: Prometheus hashes the sorted label set, metric name included, with xxHash64 ([labels_slicelabels.go](https://github.com/prometheus/prometheus/blob/main/model/labels/labels_slicelabels.go)), and VictoriaMetrics shards by consistent hashing over metric name and all labels ([cluster docs](https://docs.victoriametrics.com/victoriametrics/cluster-victoriametrics/)). Byte parity across languages checked by shared test data is known practice for canonical encodings ([RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)). Among the time-series and sketch formats checked, cross-language tests compare meaning, not bytes ([Arrow integration tests](https://arrow.apache.org/docs/format/Integration.html); [DataSketches](https://datasketches.apache.org/docs/Architecture/LargeScale.html)). What OpenTSx can state is byte parity of a time-series exchange record in Java and Python (`opentsx-model/src/test/java/org/opentsx/model/EpisodesAndWireFormatTest.java:70-79`; `python-package/tests/test_model_v2.py:95-102`), with small coverage: 2 episode vectors and 1 observation vector (`opentsx-model/src/test/resources/testvectors/wire-format.json`).
3. **One store SPI with a capability contract over three backends, plus checksum-verified replay: holds only as part of the combination.** Thanos has one StoreAPI over several backends, an Info API that declares store properties, and one acceptance test run against bucket, Prometheus, TSDB and proxy stores ([acceptance_test.go](https://github.com/thanos-io/thanos/blob/main/pkg/store/acceptance_test.go); [rpc.proto](https://github.com/thanos-io/thanos/blob/main/pkg/info/infopb/rpc.proto)). Trino and Hadoop use the same test pattern ([TestingConnectorBehavior](https://github.com/trinodb/trino/blob/master/testing/trino-testing/src/main/java/io/trino/testing/TestingConnectorBehavior.java); [Hadoop filesystem contract](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-common/filesystem/testing.html)). Log replay and snapshot time travel are established ([Kappa](https://www.oreilly.com/radar/questioning-the-lambda-architecture/); [Iceberg spec](https://iceberg.apache.org/spec/)). In OpenTSx only two of the three backends keep the Episode as written; the OpenTSDB backend is a point store tested against an emulator (`opentsx-store-opentsdb-v2/src/main/java/org/opentsx/store/opentsdb/OpenTsdbSeriesStore.java:69-70`; `opentsx-store-opentsdb-v2/src/test/java/org/opentsx/store/opentsdb/OpenTsdbEmulator.java:20-25`).
4. **Collectors with units, quality, origin class and catalogs: refuted as a distinction.** Open tools collect the same or more sources with unit harmonization, quality flags and catalog mapping: [StreamPipes Connect](https://pmc.ncbi.nlm.nih.gov/articles/PMC7250600/), [wetterdienst](https://github.com/earthobservations/wetterdienst), [entsoe-py](https://github.com/EnergieID/entsoe-py), [OpenOA](https://github.com/NREL/OpenOA), [OpenMUC](https://www.openmuc.org/openmuc/user-guide/). The origin class has a standard counterpart in the AAS ValueOriginQualifier ([IDTA 02008-1-1](https://industrialdigitaltwin.org/wp-content/uploads/2023/03/IDTA-02008-1-1_Submodel_TimeSeriesData.pdf)). In OpenTSx, Modbus runs against a simulator only and the SCADA normalizer has 5 example mappings (`opentsx-modbus/README.md:11-14`; `opentsx-windpark/src/main/resources/windpark/channel-catalog.yaml`). The collectors stay in the paper as scope and as evidence that the model applies to real public sources.
5. **Hadoop.TS nonlinear methods beside streaming sketches and pattern search: refuted as stated.** The nonlinear methods do not run on the v2 identities: in Python they take arrays, in Java the legacy model (`docs/user-manual/11-classic-analytics.md:80-95`). Each method family exists elsewhere ([pyunicorn](https://github.com/pik-copan/pyunicorn); [NeuroKit2](https://neuropsychology.github.io/NeuroKit/functions/complexity.html); [STUMPY](https://stumpy.readthedocs.io/en/latest/api.html); [DDSketch](https://doi.org/10.14778/3352063.3352135)), and Apache IoTDB runs quality checks, DTW, cross-correlation and pattern matching inside the store ([UDF library](https://iotdb.apache.org/UserGuide/latest/SQL-Manual/UDF-Libraries_apache.html)). Methods next to each other in one repository are not a contribution. Status change: [kamir/OpenTSx#254](https://github.com/kamir/OpenTSx/pull/254) (merged on 2026-11-16 as `075cbc2`) adds result types to the model and Python converters for DFA and event synchronization. That turns the analysis part into a new candidate claim C6 (Section 8.1), which is not yet tested against counterparts.

What survives is the combination of claims 1 to 3 in one Apache-2.0 code base (`LICENSE:1-2`): one record type that is identified and encoded the same way in Java and Python, stored behind one contract, replayed from a Kafka-protocol log with a completeness check, and that carries optional per-value quality, an exactly mergeable summary and provenance. No candidate record and no primary-source check found this combination. Two cautions apply. The matrix criteria for D2, D7 and D12 were written with OpenTSx in view (Section 4.2), so "only OpenTSx reaches full" is partly true by construction. And the paper has to show an effect of the combination, such as exact merge of summaries across stores and languages or verified replay from the log into Iceberg, not only its presence.

Verdict on the thesis:

- First half (domain abstraction): supported for the storage and exchange of measured series. For the analysis domain, data model 2.0 had no types for methods, parameters or results such as DFA exponents or event-synchronization matrices (9 records; `docs/user-manual/11-classic-analytics.md:80-95`). [kamir/OpenTSx#254](https://github.com/kamir/OpenTSx/pull/254) added results as data model 2.1 (`AnalysisResult` with scalars, curves and matrices, a result id shared by Java, Python and TypeScript). The first half now holds for analysis results as well, but not yet for methods as types, edge tables or surrogate tests.
- Second half (Apache Wayang as data federation over collectors): not supported. A search for `wayang` over the code and all 22 `pom.xml` files at `548f316` returns no match. The designed role of Wayang in OpenTSx is federated learning and federated structure discovery (`docs/datamodel-2026/05-SMART-TOPICS.md:147-158,273-277`), and the runtime choice is open (`docs/datamodel-2026/05-SMART-TOPICS.md:254`). Wayang itself is an Apache Top-Level Project since November 2025 ([ASF committees](https://projects.apache.org/json/foundation/committees.json); [graduation post](https://wayang.apache.org/blog/tags/tlp)) with release 1.1.1. It reaches Kafka only through KafkaTopicSource and KafkaTopicSink operators on its Java platform, and no time-series type, timestamp model or window operator was found in the 1.1.1 tag or on master ([apache/wayang](https://github.com/apache/wayang)). Any time-series semantics in a Wayang federation would have to come from OpenTSx.
- Recommendation: submit the implemented model, storage and replay layer as a system and data-model paper (Section 8.4, variant a). Claim domain-aware federation only after the Wayang-based runners are implemented and evaluated against a centralized baseline (Section 8.4, variant b).

## 3. From Hadoop.TS to OpenTSx

### 3.1 Hadoop.TS in 2013

Reference [1]: M. Kaempf and J. W. Kantelhardt, IJCA vol. 74, no. 17, July 2013, DOI [10.5120/12974-0233](https://doi.org/10.5120/12974-0233), both authors at Martin-Luther-Universitaet Halle-Wittenberg ([PDF](https://research.ijcaonline.org/volume74/number17/pxc3890233.pdf)).

Contributions, with the section of the paper:

- A Java framework of loosely coupled, reusable components for rapid prototyping of time-series algorithms (abstract, Section 1.1).
- Generic data structures for equidistant, event and inter-event series, with metadata separated from raw data (Section 6, package `hadoopts.data.types`).
- The time-series bucket: a collection of series created for one analysis, with descriptive statistics, the full preprocessing history and consistency checks before processing or merging (Section 3).
- Three modes of operation: standalone programs, MapReduce jobs and user-defined functions for Hive, Pig and Datameer (Sections 2.5, 6, 7).
- Core classes `TSBucket` (series of equal length and sampling rate, stored as SequenceFile or Avro) and `TSProcessor`/`TSOperation` (per series or per pair) (Section 7, Figs. 3-4).
- A data-flow architecture: collection with Flume and Sqoop, storage in HDFS, HBase or OpenTSDB, and an external metadata tool for process history (Section 4, Fig. 2).
- Univariate methods (autocorrelation, DFA, MFDFA, return-interval statistics) and bivariate methods (cross-correlation, event synchronization) for correlation-network reconstruction (Sections 1.2, 5, 8).
- Generators for uncorrelated and long-term correlated surrogate series (Section 9, Figs. 5-6).
- Export to CSV, XML and JSON and converters to Mahout and Giraph types (Sections 2.3, 6).

What a reviewer sees today:

- The paper reports no performance or scalability measurement (Section 9). It cannot be cited for measured scalability.
- Results are shown on synthetic surrogate data only (Fig. 6). The Wikipedia application is in [2]; financial series appear only as a cited reference.
- A bucket requires equal length and sampling rate (Section 7.1). Irregular series must be resampled.
- Series identity is application specific (HBase keys "defined in an application-specific but efficient way", Section 2.4).
- The design is batch first; streaming is described as buffered incremental updates (Section 7.1).
- Metadata management is an unspecified external service (Section 7.2). There is no metadata schema, no lineage standard and no data-quality model.

## 4. Taxonomy

### 4.1 Clusters

- A. Time-series management systems and databases: storage engines and their unit of storage.
- B. Distributed and big-data time-series processing: peers and successors of Hadoop.TS on Hadoop, Spark, Flink, Dask and Ray.
- C. Analysis and machine-learning libraries: in-memory series types and analysis methods.
- D. Federation: cross-platform processing, polystores, query federation, data spaces and federated learning.
- E. Semantic models and standards: observations, time series, assets, units, quality and provenance.
- F. Raw-data collectors: protocol access and harmonization of names, units and timestamps.
- G. Commercial industrial tools: historians, asset frameworks and operational analytics.
- H. Commercial cloud tools: managed time-series services and data platforms.
- I. Research architectures and open platforms: digital-twin and IoT platforms, co-simulation frameworks, lakehouse table formats, log-based reprocessing and stream provenance that combine storage, history and replay.

### 4.2 Dimensions

| Dimension | Question | Full (●) | Partial (◐) |
|---|---|---|---|
| D1 Series identity | How is a series identified? | Identity defined by content (name or metric plus tags or properties) | Assigned identifier: tag name, server id, UUID, user string, index level or position |
| D2 Unit of exchange and storage | What is the bounded unit of data? | A bounded unit with values and metadata used for both storage and exchange | A bounded unit for one of the two (chunk, segment, block, XML segment), or an interval object that references values held elsewhere (capsule, event frame) |
| D3 Per-value quality | Does each value carry a quality code? | Quality code per value with more than two states | Binary mask, window-level quality measures, or quality in a separate tag |
| D4 Provenance, origin class, lineage | Where does a unit come from? | Provenance record per stored unit with a parent link and an origin class | One of: source-system fields, versions, audit trail, job-level lineage, origin qualifier |
| D5 Mergeable summaries or sketches | Can aggregates be combined without raw values? | Summaries stored per unit with a stated merge rule | Precomputed or query-time aggregates without a stated merge rule |
| D6 Storage independence | One interface over several backends? | One interface or contract over several storage backends or engines | Several backends without a common contract, or references to external stores |
| D7 Replay and reproducibility | Can a past state be rebuilt exactly? | Deterministic ids or checksums plus replay or time travel | One of: versions, immutable units, time travel |
| D8 Raw-data collectors with catalog mapping | Does raw data enter through a semantic mapping? | Collectors for external sources that map raw names to a catalog or model | Collectors without semantic mapping, or a mapping without collectors |
| D9 Federation | Are queries or computation run across sources, engines or owners? | Execution across sources, engines or owners without copying into one store first | By reference, read-only union, or connectors without planning |
| D10 Analysis methods | Which method families? Letters: S statistics and aggregates, P pattern or similarity search, N nonlinear methods (DFA, MFDFA, event synchronization, recurrence), F forecasting and learning | S, P and N | A subset (letters given) |
| D11 Metadata catalog | Is series metadata in a catalog? | Publication to an open external catalog | Internal asset or context model, or catalog policies |
| D12 Language parity | Same bytes in several languages? | Byte-identical encoding in at least two languages, checked by shared test vectors | Clients in several languages without a parity statement |
| D13 Openness | Under which terms? | OSI open-source license or royalty-free open standard | Open core, or an open specification sold by a standards body |
| D14 Decision layer | Is there a twin or decision layer? | Twin or decision objects executed on data | Twin data model, link to twin products, or proof of concept |

None (○) means the record states the property is absent, or the candidate has no such layer. "◇" means designed or described, not implemented. "n/a" means not applicable to a format or standard. "n/v" means the record says nothing. A trailing "v" marks a vendor claim.

### 7.3 What OpenTSx does differently

1. The interval carries the data. Vendor intervals (capsules, event frames, context items, Canary and IDMP events) are metadata over a tag store. The OpenTSx Episode holds values, quality, summary and provenance and is itself stored, exchanged and replayed.
2. Open formats behind an interface. Episodes are Avro records on a Kafka-protocol log and rows in Iceberg, behind one store SPI. Closed services show the lifecycle risk: Azure TSI retired on 2024-07-07 ([notice](https://learn.microsoft.com/en-us/previous-versions/azure/time-series-insights/migration-to-fabric)); Timestream for LiveAnalytics closed to new customers on 2025-06-20 ([AWS](https://docs.aws.amazon.com/timestream/latest/developerguide/AmazonTimestreamForLiveAnalytics-availability-change.html)); the Google Timeseries Insights documentation returned HTTP 404 on 2026-11-16.
3. A mergeable summary per stored unit. Vendor aggregates are query-time results or window outputs.
4. Five origin classes (measured, reported, forecast, estimated, synthetic) instead of a three-state quality. The closest standard counterpart is the AAS ValueOriginQualifier, not a product.
5. Nonlinear methods (DFA, MFDFA, event synchronization, return intervals). They are not in the vendor documentation that was read; the KQL series functions, for example, do not list them ([KQL](https://learn.microsoft.com/en-us/kusto/query/time-series-analysis)).
6. Federation is not a difference today. Cognite and SiteWise copy data into their platform; Seeq and TDengine IDMP read sources through connectors; Scalytics claims in-place execution. OpenTSx has an in-process union of two stores.

### 8.1 Distinguishing claims as rewritten

#### C1. The Episode as one record for storage, exchange and replay

**Claim.** OpenTSx defines one Avro record, the Episode, that holds the values of one series over `[tStart, tEnd)` with a REGULAR time axis (start plus interval) or an IRREGULAR_DELTA axis (zig-zag varints of first delta, then delta of delta), an optional quality byte per value, a summary (valid count, NaN count, min, max, mean, m2) with an exact merge rule, a segmentation record and a provenance record with a parent episode id. The same record is written to the Kafka-protocol log, stored as one Iceberg row and replayed. An Episode is immutable per revision; a correction is a new revision of the same id.

**Status.** Implemented, with three limits. The schema fixes only quality 0 as ok; the other codes are defined per catalog, for example 0 to 4 in the wind-farm catalog. The summary is computed from the finite values and ignores the quality byte. The origin class is an episode label with two different keys, not a schema field.

**Evidence.** `opentsx-model/src/main/avro/Episode.avsc:5-22` (quality at line 16, labels at line 19, revision and provenance at lines 21-22); `opentsx-model/src/main/avro/EpisodeSummary.avsc:5-13`; `opentsx-model/src/main/java/org/opentsx/model/Summaries.java:11,33-48`; `opentsx-model/src/main/avro/Segmentation.avsc:5-17`; `opentsx-model/src/main/avro/Provenance.avsc:5-11`; `opentsx-model/src/main/java/org/opentsx/model/TimeAxis.java:24-58`; `opentsx-store-iceberg/src/main/java/org/opentsx/store/iceberg/Tables.java:59-62`; `opentsx-kafka-v2/src/main/java/org/opentsx/kafka/ReplayService.java:68-77`; `python-package/tests/test_model_v2.py:65` (merge equals summary of the concatenation; passed in the profiling run); `opentsx-store-spi/src/main/java/org/opentsx/store/SeriesStore.java:32` (latest revision); `opentsx-windpark/src/main/resources/windpark/channel-catalog.yaml:11-16` (quality codes); `opentsx-market/src/main/java/org/opentsx/market/EpisodeMapper.java:42` and `opentsx-dwd/src/main/java/org/opentsx/dwd/WeatherSeries.java:168` (origin keys `origin` and `dwd.origin`).

#### C2. Cross-language identity and encoding contract

**Claim.** The `seriesId` is the lower-case hex of xxHash64 (seed 0) over an escaped canonical form of metric and tags sorted by their UTF-8 bytes; the unit is not part of the identity. Java, Python and TypeScript recompute it against shared vectors whose hash values come from an independent xxHash package. Java and Python encode Episodes and Observations to the same bytes in Avro single-object encoding without a schema registry, with map keys written in UTF-8 order, and both suites compare against the same vectors.

**Status.** Implemented, with limits. Coverage is small: 7 xxHash vectors, 6 series-id vectors, 6 schema fingerprints, 2 episode vectors (one regular, one irregular) and 1 observation vector. Byte parity covers Java and Python; TypeScript checks the series id only. Deterministic episode ids exist in Java only. Schema evolution was never exercised: one released version, v2.0.

#### C6. Analysis results as typed records with a shared identity (new)

**Claim.** Results that are not time series are v2 records of their own. `AnalysisResult` names the method, its version, typed parameters (long, double, string, array of doubles) and the ordered input episodes and series. It carries scalars with standard error and fit range (a DFA exponent), curves over a non-time axis (F(s)) and matrices over series ids (event-synchronization `Q` and `q_directed`). Its `resultId` is the xxHash64 of a canonical form of method, version, typed parameters and inputs, so the same run on the same episodes gets the same id in Java, Python and TypeScript. That id also deduplicates results on a log without compaction or an idempotent producer.

**Status.** Implemented in [kamir/OpenTSx#254](https://github.com/kamir/OpenTSx/pull/254), merged into `master` on 2026-11-16 as `075cbc2`. On the PR head before the merge: `xvfb-run --auto-servernum mvn -B -ntp verify` passed with 642 tests in 22 modules; the Python suite passed with 108 tests; the frontend suite passed with 207 tests.

**Evidence.** Schemas `opentsx-model/src/main/avro/AnalysisResult.avsc`, `ResultScalar.avsc`, `ResultCurve.avsc`, `ResultMatrix.avsc`, frozen as `schema-history/v2.1`; identity in `AnalysisResults.java`, `python-package/opentsx/model/analysis.py` and `opentsx-saas-frontend/src/workbench/resultIds.ts`; vectors `testvectors/result-id.json` (9 cases) and the `analysisResults` entries of `wire-format.json` (byte-identical Java and Python encoding); converters `python-package/opentsx/algorithms/results.py`; normative text in `docs/datamodel-2026/04-MODELL-V2-SPEC.md`, Section 8.

**Closest counterparts, to be checked before the claim is used.** sktime types tasks and in-memory containers, not stored results (Cluster C). OGC TimeseriesML and the AAS TimeSeries submodel type observed series, not analysis output (Cluster E). Experiment trackers record runs and metrics under generated run ids. Whether any of them defines stored, typed analysis results with an identity derived from method, parameters and inputs was not checked in this study.

**Verdict.** Candidate claim. It holds only if the counterpart check finds no equivalent.

**Use in the paper.** As the analysis-domain half of the data-model contribution in variant (a), with the cross-language vectors as the evidence.

#### The combination

**Statement.** C1 to C3 in one Apache-2.0 code base (`LICENSE:1-2`): one record type that is identified and encoded the same way in Java and Python, stored behind one contract, replayed from a Kafka-protocol log with a completeness check, and that carries optional per-value quality, an exactly mergeable summary and provenance.

**Why it differs.** The closest candidates each cover part of it. Thanos covers label identity, one store interface with a shared acceptance test, and object storage, but not per-value quality, per-unit summaries or provenance. The AAS template covers bounded segments with value quality and value origin, but no identity hash, merge rule, storage contract or replay. IoTDB and TsFile cover bounded chunks with statistics, quality functions and SDKs in three languages, but not per-value quality in the unit or provenance. Cognite and SiteWise cover per-value quality and collectors in closed services. No candidate record and no primary-source check covers all three claims.

**Objections a reviewer will raise, and the answer.**

1. "A combination of known parts." State the contribution as a system and data-model contribution and measure an effect that the parts do not give alone: exact merge equality of summaries across episodes, stores and languages; exchange between a Python producer and a Java consumer with agreement on id and bytes and no registry; replay of a sealed bucket from the log into Iceberg with a matching checksum. All three can be measured on the existing code.
2. "The matrix favors OpenTSx." The full marks for D2, D7 and D12 were defined with OpenTSx in view (Section 4.2). State the criteria before the comparison and report where others match or lead: Thanos, Wayang and BigDAWG lead on D6 and D9; products and StreamPipes lead on D8; TimeseriesML, AAS, Cognite and SiteWise match on D3; BTrDB matches on D5 (Section 6).
3. "Search coverage." 161 candidates and 20 primary-source checks on 2026-11-16. Absence of a counterexample is not proof; the paper should say so.

### 8.4 Recommended contribution statement

#### (a) What can be claimed today: a system and data-model paper

Proposed text: "OpenTSx is an open-source system for measured time series that continues Hadoop.TS. Its central record, the Episode, holds the values of one series over a bounded interval together with an optional quality byte per value, a summary with an exact merge rule and a provenance record with a parent link, and the same record is used for storage, exchange and replay. Series identity is a hash of a canonical metric and tag form that Java, Python and TypeScript recompute identically, and Java and Python encode records to identical bytes without a schema registry, checked by shared test vectors. One storage interface with declared capabilities and a shared contract test covers an in-memory, an Apache Iceberg and an OpenTSDB backend, of which the first two keep episodes as written, and sealed buckets on a Kafka-protocol log are replayed with a completeness check. Ten collector classes map public energy and weather sources, meter registers, wind-farm SCADA names and legacy Hadoop.TS buckets into the model. Each of these elements has precedents; the contribution is their combination in one record type and one code base, and we report what the combination allows: exact merge across stores and languages, registry-free exchange, and verified replay."

Evidence the paper needs before submission, all on the existing code:

1. Merge equality: summaries and DDSketch bytes merged from many episodes, in Java and in Python, equal the summary and sketch of the concatenated values, the sketch while below its bin limit; report the floating-point bound for mean and variance (`python-package/tests/test_model_v2.py:65`; `python-package/tests/test_stats.py:14`).
2. Exchange: a Python producer and a Java consumer agree on ids and bytes over KafScale without a registry; extend the vectors beyond 2 episodes (`opentsx-model/src/test/resources/testvectors/wire-format.json`).
3. Replay: a sealed bucket replayed from the log into Iceberg gives a matching checksum and count; report replay throughput on object storage (`opentsx-kafka-v2/src/main/java/org/opentsx/kafka/ReplayService.java:68-77`).
4. Storage cost as measured (`opentsx-kafka-v2/README.md:62-72`), and the limits of Section 8.2, points 3 to 8.
5. Analysis results ([kamir/OpenTSx#254](https://github.com/kamir/OpenTSx/pull/254)): the result-id vectors pass in Java, Python and TypeScript, DFA and event-synchronization output round-trips as `AnalysisResult`, and a comparison of expressiveness with sktime, TimeseriesML and the AAS TimeSeries submodel (C6).

Do not claim in variant (a): federation, scale, per-value origin in stored data, quality-aware aggregation, distinct collectors or analysis methods, or abstraction of the analysis domain beyond result types. Result types (C6, [kamir/OpenTSx#254](https://github.com/kamir/OpenTSx/pull/254)) may be claimed once the counterpart check is done.

#### (b) What can be claimed after the Wayang-based federation is implemented and evaluated

Target architecture (the owner's plan; no repository document describes it yet, and the closest design note only allows Go or Rust edge collectors, `EVOLUTION/TASK-011-datamodel-refresher-2026.md:161`): at each decentralized site a runner that talks only Kafka (a Java runner on Wayang's Java platform with KafkaTopicSource and KafkaTopicSink, or a Rust runner that executes the site part of a Wayang plan, which needs a new platform module because Wayang 1.1.1 has none for Rust) reads Episodes from the local KafScale log, computes mergeable aggregates per series and window (EpisodeSummary, SeriesStats with DDSketch, data-quality verdicts, bucket checksums) and writes only those aggregates to a central signal cluster, where they are merged.

Proposed text, to be filled with measured values: "We extend the Episode model to federated execution. Apache Wayang plans the analysis; Kafka-only runners at each site compute mergeable summaries, quantile sketches and quality checks over local episode logs, and only these aggregates, keyed by the shared series id and carrying provenance, travel to a central cluster. For mergeable statistics the federated results equal the centralized results within [bound]; the data moved across sites falls by a factor of [measured] at a latency of [measured] and a throughput of [measured] compared with centralized ingestion."

Required evaluation:

1. **Setup.** At least two sites, better 2, 4 and 8, each with its own KafScale cluster and collectors; one central cluster. Workload: the wind-farm simulator with ground truth (10 turbines, 6 h at 1 Hz, 17 events; `opentsx-windpark/README.md:118-133`) split across sites, plus archived DWD and market data, plus one real dataset if one can be published. Hardware, versions and scripts published; inputs as sealed buckets with checksums.
2. **Baselines.** Centralized: all raw episodes shipped to the central cluster and processed by the existing statistics processor or Flink job (`opentsx-flink-core/src/main/java/org/opentsx/flink/stats/StatsJob.java`). Query-time federation that pulls raw series at query time, in the manner of Thanos. A hand-wired Kafka consumer pipeline that performs the same merges without Wayang.
3. **E1, federated equals centralized for mergeable statistics.** For every series and window: valid count, NaN count, min and max identical; mean and variance within a stated floating-point bound, since the Chan merge is exact only up to rounding; DDSketch bytes identical to the sketch of the union as long as no store exceeds the bin limit, after which the smallest bins collapse (`opentsx-stats/src/main/java/org/opentsx/stats/QuantileSketch.java:33,54`), and quantiles within the relative-error bound alpha of the exact quantiles ([DDSketch](https://doi.org/10.14778/3352063.3352135)); data-quality verdicts identical; bucket checksums of the contributing episode ids identical. Repeat with late data, duplicates (KafScale has no idempotent producer, so duplicates must be removed by episode id; `opentsx-kafka-v2/src/main/java/org/opentsx/kafka/KafScaleClients.java:19-20`) and one site offline.
4. **E2, data moved.** Bytes crossing site boundaries per hour, federated against centralized, as a function of series count, sampling rate and window length, with the raw episode cost of 2.18 B per value as reference (`opentsx-kafka-v2/README.md:62-72`).
5. **E3, latency.** Time from the source timestamp to the merged aggregate being readable in the central cluster, p50, p95 and p99, for the federated setup and each baseline.
6. **E4, throughput.** Values and episodes per second per site runner and at the center, scaling over sites and partitions, with CPU and memory of the site runner.
7. **E5, limits.** Which statistics cannot be merged exactly (exact median, DFA and MFDFA exponents, event-synchronization matrices) and how they are handled: sketch approximation, or local computation with only results exported.
8. **E6, what Wayang adds.** Compare the Wayang-planned deployment with the hand-wired pipeline. If the plan, placement or cost does not differ, Wayang is a deployment choice and not part of the contribution.

Positioning for variant (b): decomposable aggregates have been computed near the data since TAG ([SIGOPS OSR 36](https://doi.org/10.1145/844128.844142)), and cross-platform planning is the subject of Rheem and Wayang [20], [21] ([PVLDB 11(11)](https://doi.org/10.14778/3236187.3236195); [SIGMOD Rec. 52(3)](https://doi.org/10.1145/3631504.3631510)). The claim in (b) can therefore only rest on the domain semantics: aggregates keyed by a shared series id that keep quality and provenance, completeness checks across sites through bucket checksums, and results equal to centralized processing. The Scalytics site describes Wayang as its decentral processing layer and lists the KafScale engine as its open-source component ([vendor page](https://www.scalytics.io/federatedintelligence)), and OpenTSx runs on KafScale (`opentsx-kafka-v2/src/main/java/org/opentsx/kafka/KafScaleClients.java:15-20`); if an author is affiliated with Scalytics, the paper needs a competing-interest statement.

## 10. Proposed related-work section and references

### 10.1 Structure

II. Related Work

- A. From Hadoop.TS to distributed time-series analysis: [1], [2], [10] to [14]. Hadoop.TS contributions and limits (Section 3.1); Spark, Flink and Kafka Streams successors; three of them cite [1]. spark-ts and Flint have no paper; cite each once as a web reference (Section 5, B).
- B. Time-series management systems and their storage units: [3] to [9]. Taxonomy of [3]; storage units of [4] to [8]; evaluation method of [9]. Point: storage units are compression or partition units, not exchange units with quality and provenance.
- C. Data abstractions in analysis libraries: [15] to [19]. sktime and Darts as typed analysis abstractions; pyunicorn, DFA [18] and MFDFA [19] as the method lineage of Hadoop.TS. Point: in-memory types without persistent identity or provenance.
- D. Standards for observations, time series and provenance: [25] to [31]. OMS and its encodings, the AAS time-series submodel, SSN, PROV-O, IEC 61400-25-2. Point: TimeseriesML and AAS segments are the closest counterparts of the Episode; give a field-level mapping.
- E. Collection and semantic harmonization: [32] to [34], [31]. Point: harmonization of events or tables, not of a bounded unit with quality and origin.
- F. Federation and federated learning: [20] to [24], [35] to [37]. Cross-platform processing from the Rheem origin to Apache Wayang, polystores, federated learning on wind data. Point: no time-series semantics; position OpenTSx federation as designed future work.
- G. Commercial interval abstractions: Seeq, PI event frames, Cognite, SiteWise as web references to vendor documentation (Section 7.1). Point: intervals as metadata over tag stores.
- H. Open platforms, replay and stream provenance: [38] to [41], [6], Eclipse Ditto as a web reference. Twin platforms keep current state and history in separate stores; Kappa reprocessing re-reads a retained log; GeneaLog records tuple-level provenance. Point: none combines a persisted, checksummed exchange unit with episode-level provenance.
- I. Positioning: a reduced matrix with OpenTSx, Hadoop.TS, TimeseriesML, AAS, Chronix, ModelarDB, BTrDB, Thanos, Wayang, BigDAWG, Seeq and Cognite over D1 to D9 and D12.

Proposed contribution statement: "OpenTSx extends Hadoop.TS from a batch bucket of equal-length series to an open, replayable exchange model for measured series. Its Episode carries values, time axis, per-value quality, a mergeable summary and provenance; its series identity and encoding are byte-identical in Java and Python; one storage contract covers several backends; and collectors map public energy and weather sources into the model. Federation through Apache Wayang is designed and left for future work."
